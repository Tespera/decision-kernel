# 场景细则写法（可选层）

决策内核分两层：

- **内核**（常驻）：判据。每条 = 为什么 + 遇到取舍时问自己 + 边界。要短，要能推出没写过的场景。
- **场景细则**（按需查阅）：某条内核在具体场景下**怎么用**。比如 K4「按可逆性分配谨慎」落到「删数据」「推送到远端」「一次做完还是分批」上各是什么做法。

细则不常驻，AI 遇到具体场景时才去读，所以可以写得比内核具体得多，而不撑大每个会话的上下文。
用 `dk init --details [目录]` 启用（默认 `~/.claude/decision-kernel-details`），`dk details` 查看。

## 什么进细则，什么不进

一条发现只去一个地方：

| 去向 | 写什么 | 门槛 |
|---|---|---|
| 内核 | 新的判据、新的边界、冲突裁决的调整 | 新模式 ≥3 次证据或跨 ≥2 项目；相悖找到了隐藏条件 |
| 场景细则 | **已有内核**在某个具体场景下的做法：已被内核覆盖的裁决里，出现了细则还没写过的具体做法 | 单次即可，用户确认后写 |
| `watchlist.md` | 可能是一条新判据或新边界，但证据还不够 | 证据攒够后在下次复盘升进内核 |

判别口诀：它是**内核的用法** → 细则；它**可能是一条新判据** → 观察清单；证据够了 → 内核。

细则只写已有内核的用法。**不要借细则偷偷加新判据**——那会让常驻的内核和按需的细则说两套话。

## 文件组织

- 目录不要放在 `~/.claude/rules/` 下：那里的 `.md` 会被 Claude Code 全部常驻加载（`dk init` 会拦）。
- 一条内核一篇，文件名以编号开头，如 `K4-reversibility.md`。几条相近的内核也可以合成一篇，在开头的「依据」行列出全部编号。
  `dk details` 从文件名和第一个场景标题之前的部分识别对应哪些内核。
- 没出现过的用法不写。某条内核暂时没有细则是正常的。
- **内核里必须有一行指引**，告诉 AI 去哪读细则，否则细则写了也没人读。放在总则下面，例如：
  `需要某条内核在具体场景下的做法时，读 ~/.claude/decision-kernel-details/ 里对应编号的细则。判据在内核，用法在细则。`
  `dk details` 会检查这一行在不在。

## 每篇的格式

```markdown
# K4 · 按可逆性分配谨慎 —— 场景细则

依据：K4。内核是判据，本文是用法。

## 删除

- 不确定还有没有用的，保留；有可逆的等价做法就用它：停用代替删除、并存代替覆盖。（J1-003、K2-017）
- 确认没用的，删干净，不留「不碍事」的残留。（K1-042）

## 一次做完还是分批

- 判据是有没有回退路径、会不会影响别人，不是改动大小。（J3-011）

## 反向证据

- 「改坏了 git 回退就是，这种事不用每步都问。」——可逆的事放手做，判据是可逆性，不是事情看起来大不大。
```

- 每个场景一个二级标题（`dk details` 按它计数），下面是具体做法。
- 做法后面括号注明依据的裁决记录 id，以后质疑「凭什么这么做」能回到工作目录查原话。
- 不写项目名和业务对象：细则要能在任何项目里用。
- 可以引一两句原话作「反向证据」，说明这条用法的边界在哪。细则只在本机、按需读，不像内核那样每个会话都带着。
