# 方法：从会话记录到决策内核

这份文档记录这套方法是怎么来的、为什么长成现在这样、以及踩过的坑。数字来自作者本人的第一次蒸馏（2026-08）和之后两次增量复盘。

## 要解决的问题

用 AI 写代码的人，每天都在回答 AI 的问题：用哪个方案、要不要先备份、这里改不改、文档写多细……
同类问题反复出现，每次都得重新拍板。累的不是某一次决定，是**同一类决定做了几十遍**。

目标不是让 AI「完全不问」，而是把剩下的提问从「替我做决定」降级为「点个头」：
能按我的判断方式推出来的，它自己定，结果里说一句「按你的习惯选了 X」；真正只有我能定的（不可逆的、对外的、缺业务事实的、方向性分叉），再来问。

## 第一版为什么失败：规则清单

第一次蒸馏按常规思路走：把裁决按场景聚类，每类写一条规则。产出 **37 条规则**，被否掉了。原话是：

> 规则太死，AI 遇到没覆盖的场景没法用。

复盘发现两个根本问题：

1. **规则只覆盖写过的场景。** 「方案确定就一口气做完」管得了写代码，管不了写文档、出方案、改配置。AI 遇到没写过的场景，要么硬套，要么回来问。
2. **按场景聚类会把最强的动机拆碎。** 作者最强的一条动机是「要最佳解，不要能用的解」（46 条裁决、12 个项目），按场景聚类后被拆进了 5 条不同的规则，**哪一条都看不出它**。

## 第二版：决策内核

改成只写**判断依据**，不写行为规则。每条内核三段：

- **为什么**：动机。我在乎什么、在保护什么、算的是哪笔账。
- **遇到取舍时问自己**：几个提问。AI 用它们推出没写过的场景该怎么做。
- **边界**：什么时候不适用，和相邻内核怎么分界。

外加一段**冲突裁决**：多条内核同时命中时谁优先（例如「可逆性压倒一切」）。

最终是总则 + 11 条内核 + 8 条冲突裁决，约 300 行，常驻在每个会话里。成品见 `examples/decision-kernel.md`。

两个刻意的约束：

- **内核正文不写原话、不写项目名和业务对象。** 它要能被任何项目直接引用；写进业务对象，AI 就会把它当成那个项目的专属规则。原话和证据另存在工作目录的溯源表里。
- **动机要有用户自述撑着，不能由 AI 反推。** 第二轮专门从 139 条含理由的片段里挖出 125 条动机陈述，逐条核对每条内核的「为什么」确实有用户亲口说过的理由。

### 可选的第二层：场景细则

内核要短，才能常驻、才推得出没写过的场景。但归纳时总会遇到另一类东西：某条内核在具体场景下**怎么用**（K4 落到「删数据」「推送到远端」各是什么做法）。
放进内核会撑大常驻内容，扔掉又可惜。作者的做法是另开一层**场景细则**：按内核分篇，不常驻，AI 遇到具体场景时按内核里的一行指引去读。

一条发现只去一个地方：新判据、新边界进内核（要过证据门槛）；已有内核的具体用法进细则（单次即可）；可能是新判据但证据不够的进观察清单。
细则只写用法，不借它加新判据，否则常驻的内核和按需的细则会说两套话。这一层是可选的：`dk init --details` 启用，写法见工作目录里的 `DETAILS_GUIDE.md`。

## 流水线

```
本地记录 ──scan──▶ 决策片段 ──Claude 抽取──▶ 裁决记录 ──verify──▶ 可信记录
                                                                   │
              内核 ◀──用户逐条确认── 初稿 ◀──Claude 按动机归纳── 动机陈述 + 权衡轴清单
               │
               └── evidence：每条内核由哪些记录、哪些动机支撑（溯源表）
```

### 1. 硬筛（`dk scan`，纯规则，零 LLM）

两个来源，互补：

| 来源 | 内容 | 保留时长 | 能抽什么 |
|---|---|---|---|
| `~/.claude/projects/**/*.jsonl` | 完整对话 | 会被定期清理 | AskUserQuestion 问答、Claude 征询后的回答、对 Claude 动作的反应、协作元反馈 |
| `~/.claude/history.jsonl` | 只有用户输入 | 长得多 | 协作元反馈、强纠正 |

两源按正文前 120 字去重。系统以 user 身份注入的文本（提醒、技能说明、上下文续接摘要）必须剔掉——它们不是用户的话，混进去会污染「用户原话」这一核心证据。

第一次：340 万字符 → 1377 个片段（压到 24%）。

### 2. 抽取（Claude / subagent，按 `EXTRACT_GUIDE.md`）

每个片段转成结构化记录，核心字段是 `verbatim`（逐字原话）和 `axis`（这次在哪条权衡轴上取舍，写成「A > B」）。
抽取者是**转录员，不是分析师**：判断只能出现在 axis / domain / reusable / confidence 四个字段里，拿不准就丢。
预期丢弃 40–60%。第一次：1377 片段 → 784 条记录，8 个 subagent 并行。

### 3. 原话校验（`dk verify`）

每条 `verbatim` 必须能在原始片段的**用户侧字段**里原样找到。第一次跑出来：96.6% 精确命中，
13 条是用省略号连接的摘录（各段都在原文里，算通过），3 条把上一轮的话当成了这一轮，**1 条是 subagent 给原话续写了一句**。
最后这种如果放过去，就是「AI 替用户发明原则」——这正是整套方法最想避免的事故。所以这一步是闸门，不能跳。

### 4. 归纳（主会话，人在环）

`dk axes` 把记录压成一行一条的权衡轴清单，供通览。归纳由主会话做，原因：

- **自动聚类在中文上失败了。** 用字符串相似度对权衡轴聚类，784 条记录聚成 744 组，几乎没合并——中文短语换个说法字面就完全不同。语义归纳只能交给模型和人。
- **反例要解释，不能投票。** 同一条轴上出现相反的裁决时，不取多数：先找隐藏条件（「只影响自己时放手做，影响他人时先问」），那通常就是内核的边界。
- **只留可迁移的。** `reusable: false`（绑死在某个项目上）的不进内核。新内核要 ≥3 条独立证据或跨 ≥2 个项目。

### 5. 逐条确认

初稿交给用户逐条审。第一次的修改里最有代表性的两处：「范围严限」被纠正为「补完要做、扩展先说」；两条内核的边界撞车被指出后，改成三个提问的判据。这些都是 AI 自己归纳不出来的——**内核的最终形态必须由本人确认**。

### 6. 溯源（`dk evidence`）

`kernel_map.jsonl` 记录每条裁决归到哪条内核，生成 `evidence-map.md`：每条内核有多少条记录、来自几个项目、时间跨度、动机摘要。
以后质疑某条内核「凭什么」，从这里回查原话。

## 增量复盘（`/decisions`）

内核不是一次写完的。每隔几周跑一次，只扫上次之后的新会话，对每条新裁决判断：已覆盖 / 新模式 / 相悖 / 提问行为偏差。

- 第一次增量：288 片段 → 152 条记录，150 条已覆盖、2 条提问行为偏差，0 新模式 0 相悖。逐条判定由两个 subagent 按「内核的提问能否直接推出这条裁决」完成，主会话复核被标记的条目。这批记录有 98 条早于内核定稿，不算严格的样本外检验。
- 第二次增量：541 片段 → 330 条记录，出现 2 个新模式、1 处相悖，加了两处试行修订，其余候选进观察清单（`watchlist.md`），证据攒够再加。

「提问行为偏差」是最直接的效果指标：内核已经能推出答案、AI 却还在问，说明那条内核的措辞不够可操作。

## 踩过的坑

- **把 AI 的归纳当成用户的原则。** 一条 AI 自己贴的标签被当成「用户铁律」写进长期记忆，之后被反复引用、还拿来做架构决策，最后发现用户从没这么说过。所以：原话必须可校验，推断必须标注。
- **写成规则。** 每次修订内核都要自问：这是动机和判据，还是又写成了「遇到 X 就做 Y」？
- **会话记录会被清理。** Claude Code 默认只保留 30 天会话日志（`cleanupPeriodDays`，可在 `~/.claude/settings.json` 调大），删了就没法重新抽取。`incr-*/` 里的语料是原话的唯一副本，不要当成可随时重建的中间产物删掉。
- **为凑数加内核。** 单次出现的裁决进场景细则（内核的用法）或观察清单（可能的新判据），不进常驻内核。常驻内容越多，AI 越抓不住重点。

## 局限

- 筛选正则是针对中文对话调的。英文会话能跑，但命中率会低，需要扩充 `filters.py`。
- 依赖 Claude Code 的本地日志格式（`~/.claude/projects/*.jsonl`、`history.jsonl`），格式变了需要跟着改。
- 抽取和归纳依赖模型质量与人工确认，脚本只负责机械环节和校验闸门。
